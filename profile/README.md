<p>机房线路断掉这件事，经历过一次就忘不了：正在跑的批量任务停在半路，页面转圈，日志最后一行是三分钟前。吃过亏之后才明白，能救命的不是「永不断线」，而是「断了多久能被发现、多久能切走、切走之后会话还能不能接上」。这篇按故障树的思路拆，先分清断在哪一跳，再讲切换的条件和续跑的动作。</p>

<h2>一、先分清是「断」还是「卡」</h2>
<p>这两种状态的处置方式完全相反。断了要立刻切，卡了要等一等，一卡就切反而会把本来能恢复的会话彻底放弃，还得重做一遍。</p>
<h3>三个信号判断真假断线</h3>
<p>看连接状态、看丢包、看心跳。连接处于已建立但无数据，多半是卡；连接被对端关闭，是断；心跳连续三次无响应且路由追踪在中途某个节点全部超时，基本可以判定链路断。</p>
<h3>卡住的时候先等九十秒</h3>
<p>跨境线路在晚高峰出现几秒到几十秒的停顿很常见。设一个九十秒的容忍窗口，窗口内不动作。这个窗口能过滤掉大部分假故障，代价只是九十秒。</p>

<h2>二、断点在哪一跳，决定你该做什么</h2>
<p>故障树往下的第一个分叉就是断点位置。四个位置：本机、接入运营商、跨境链路、对端机房。位置不同，能做的动作差别很大。</p>
<h3>本机与局域网：最先排除</h3>
<p>先看本机是否能访问其他站点。能访问说明不是本地断网；全都不能，问题在本地，切备用线路也没用。这一步十几秒，但能挡掉三成误判。</p>
<h3>接入与跨境：看丢包落在第几跳</h3>
<p>用路由追踪看丢包起始位置。丢包出现在第一到第三跳，问题在本地或接入；出现在中间某跳且之后全部不通，是跨境链路；只有最后一两跳不通，可能是对端。</p>
<h3>对端：你只能等或换路径</h3>
<p>对端机房出问题时，任何本地动作都无效。这种情况下切备用线路的意义在于换一条到对端的路径，有时能绕开拥塞段，有时绕不开。切完观察五分钟，不通就退回。</p>

<h2>三、切换动作：条件、执行人、记录</h2>
<p>切换本身不难，难的是没人决定什么时候切。所以我给切换定了一条硬规则：满足任意一条即切，不需要讨论。</p>

<h3>三条触发条件</h3>
<p>一，连接被对端关闭且连续两次重连失败；二，心跳连续三次无响应且超过九十秒容忍窗口；三，路由追踪显示跨境节点全丢包持续三分钟。三条任意一条成立，直接切。</p>
<h3>谁来决定</h3>
<p>有人值守时由当班的人决定；无人值守时由脚本自动切，规则写死在配置里，不要留「视情况而定」。自动切换要设上限：一个小时内最多切两次，超过就停下来告警，避免来回横跳。</p>
<h3>切换必须留三条信息</h3>
<p>切换时间、原出口、新出口。三条写进日志，事后复盘全靠它。没这三条，你只知道切过，不知道切了多久、切了几次。</p>

<h2>四、切换之后，会话怎么接着跑</h2>
<p>很多人的切法是「断了重来」，这在小任务上没问题，在长任务上等于白跑。能不能续，取决于事前有没有做三件事。</p>
<h3>第一件：任务要能断点续跑</h3>
<p>把长任务切成小段，每段完成后写一条进度记录。切换之后从最后一条记录往后接着跑。段的大小按十分钟左右划分，太粗等于没有，太细写日志本身成为负担。</p>
<h3>第二件：状态要落在本地</h3>
<p>进度、已完成列表、待处理列表都存在本地文件里，不要只存在内存或会话里。会话一断，内存里的东西全没了，这是最常见的数据丢失方式。</p>
<h3>第三件：切换后先做一次轻量校验</h3>
<p>新出口启用后，先发一个短请求确认链路通，再继续跑长任务。跳过这一步直接续跑，失败了又要重切一次，来回折腾。</p>

<h2>五、切换也失败的时候怎么办</h2>
<p>备用线路同样不可用，说明问题超越了你手上的两条线。这时要做的是止损，而不是继续折腾。</p>
<h3>先停下写入类任务</h3>
<p>所有会改变状态的任务立即暂停，包括提交、发布、扣费类操作。网络不稳的时候继续写入，容易产生重复或不完整的数据，比停下来麻烦得多。</p>
<p>把现场存下来。存三样：日志、当时的出口地址、路由追踪结果。这三样在报障时能省掉大量来回问答，也是事后判断责任的依据。</p>
<p>按影响面决定要不要换供应商。同一个问题在一个月内出现三次以上，且对方给不出具体原因，才考虑换。偶发一次就换，成本比收益高，而且新供应商未必更好。</p>

<h2>常见问答</h2>
<h3>切换备用线路会不会影响账号环境？</h3>
<p>答：会，出口地址变了就是一次环境变化。所以备用线的地址应当提前登记，切换后同步更新台账，让记录和现实保持一致，否则下次排查会拿错基线。</p>
<h3>自动切换会不会太敏感？</h3>
<p>答：设好门槛就不敏感。关键是三条触发条件都要有明确的次数或时长，而不是「一次失败就切」。同时要有小时上限，防止在两条坏线之间来回横跳。</p>
<h3>断线期间收到的一半结果要保留吗？</h3>
<p>答：保留但标记为未完成。完整的结果可以直接用，半截的结果必须重跑，否则后续处理会基于不完整数据，错误会一路传下去。</p>
<h3>怎么知道备用线路本身是不是好的？</h3>
<p>答：平时就让备用线跑低优先级任务，保持活跃并持续产生日志。完全不用的备用线，真到切换时才发现它也是坏的，这种事故并不少见。</p>
